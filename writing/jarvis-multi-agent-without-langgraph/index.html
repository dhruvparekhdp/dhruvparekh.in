Why my multi-agent system doesn't use LangGraph (yet)

Jarvis plans its own work, runs across my machines and asks before anything destructive. I wrote the orchestration myself instead of pulling in a framework. Here's the reasoning.

Dhruv Parekh·17 Oct 2026·5 min read

Jarvis is the AI assistant I run at home. Give it a goal and a planner breaks it into a graph of tasks. Specialist agents work through that graph under permission and budget limits. Branches that don't depend on each other run at the same time. Other machines in the flat join as worker nodes.

The obvious way to build this in 2026 is LangGraph. I didn't use it, or LangChain. This is why, and what I built instead.

The decision, in the repo's own words

Every non-obvious choice in Jarvis is written down in docs/DECISIONS.md. This one is titled "No LangGraph yet". The "yet" matters.

The scheduler is a dependency-driven loop over a persisted task graph; a graph library would wrap that rather than simplify it, and persistence, leases and budgets are the parts that actually matter.

Put plainly, the hard parts of an agent system aren't drawing the graph. They are what happens when the process dies halfway, when a model loops forever, or when an agent wants to delete something. A framework doesn't solve those for you. You still write them, and then you also maintain the framework.

The repo has a shorter rule for dependencies in general: write the logic, import the plumbing. FastAPI, the database driver and the embedding model are imported. The orchestration is written.

Agents are files, not classes

Every agent is a YAML file: a prompt, a tool list, a capability grant and a budget. One generic runner executes all of them. There are five today: assistant, planner, research, operator and memory. Adding one means adding a file. Here's the whole assistant:

id: assistant
name: Assistant
description: General conversation and anything that needs no specialist.

system_prompt: |
  You are Jarvis, a personal AI assistant, handling a task directly.

  Style:
  - Warm, direct, and brief. Two or three sentences unless more is genuinely useful.
  - Talk like a person, not a manual. Never open with "As an AI".
  - If the task needs a capability you do not have, say so plainly rather than
    pretending to have done it.

tools: [memory.search, memory.read]
capabilities: [READ]

model_preference: fast

budget:
  max_tokens: 12000
  max_seconds: 60
  max_tool_calls: 4

Definitions are validated at boot, so a typo in a tool name fails at startup instead of halfway through a mission.

Agents can't start work

Runaway recursion is the classic multi-agent failure: an agent spawns an agent, which spawns another. In Jarvis it isn't discouraged. It's impossible. The runner only gives a model the schemas of the tools it's allowed. Starting work isn't one of them. Only the scheduler dispatches.

"""Mission scheduler -- the only thing that dispatches work.

Centralising dispatch here is what makes the spec's anti-recursion rule
structural rather than aspirational: agents have no way to start work, so every
delegation passes through one audited place that can refuse it.

Every mission also has a hard budget, checked before each dispatch:

Per-mission limitDefault
Tasks12
Tokens120,000
Wall-clock time300 s
Tool calls40

Each agent has its own smaller budget on top of that, and the runner stops any single task after eight model round-trips.

Permissions live at the tool, not in the prompt

Telling a model "don't delete files" is a suggestion. Jarvis enforces it in code. Every tool carries a capability (READ, WRITE, EXECUTE or FINANCIAL) and a risk level (SAFE, SENSITIVE or DANGEROUS). A call goes through only if the tool is on the agent's list and the agent holds that capability.

DANGEROUS tools never run on their own. Today those are memory.forget, fs.delete and shell.exec. The task parks as needs approval and I approve or deny it from the app on my phone. If I don't answer within ten minutes, that counts as no.

Crashes cost latency, not work

State is written at every transition. A running task holds a lease of 180 seconds. On boot, any task whose lease has lapsed goes back to ready:

for row in orphans:
    lease = _parse_ts(row["lease_expires_at"])
    # No lease, or one that has already lapsed -> nobody is working on it.
    if lease is None or lease <= now_dt:
        execute(
            conn,
            "UPDATE tasks SET status = ?, lease_expires_at = NULL, updated_at = ?"
            " WHERE task_id = ?",
            (TaskStatus.READY.value, now, row["task_id"]),
        )
        requeued += 1

Honest gap: tasks are requeued on boot, but a resumed mission doesn't restart by itself yet. The work is ready and nothing kicks the scheduler. It's a small fix I haven't made yet.

Machines dial out

Worker machines open an outbound WebSocket to the orchestrator. Nothing listens on an open port, so there's nothing to port-forward and nothing to scan. A node advertises what it can do. The scheduler places work by capability and prefers idle machines with the most memory. It never picks by hostname. Each node also keeps its own file-path jail and shell allowlist.

Memory without a vector database

Search mixes two rankings. Keyword ranking is a hand-written BM25. Semantic ranking is cosine similarity over local embeddings from all-MiniLM-L6-v2, 384 dimensions, run on-device. The two lists are merged with reciprocal rank fusion.

The vectors sit in an ordinary text column and are compared by brute force. At personal scale that's fast enough, and it's one less service to run. If the embedding model isn't available, search falls back to keyword-only and says so.

Tests

176 tests, all offline. The test setup strips API keys and uses a throwaway SQLite file, so the suite costs nothing to run. The same suite runs against Postgres by setting one environment variable.

When I'd add LangGraph

When the problem changes shape. Right now work flows one way: router → runner → scheduler. The coding and device agents on the roadmap will need real cycles. From the same decision record:

The nodes are already separated (router → runner → scheduler), so adopting it when the coding and device subsystems introduce genuine cycles stays a contained change.

The framework question isn't which one. It's whether I need one yet.
