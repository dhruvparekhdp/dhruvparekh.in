A Navratri scoreboard for 42 people who can open DevTools

I'm on the office fun committee. This year I built the scoreboard. Small app, real users, and an audience that includes testers.

Dhruv Parekh·17 Oct 2026·4 min read

Navratri at the office is nine days and nine colours. Wear the day's colour and your team scores. A small committee runs it: one person from each department. I'm on it, and I'm the engineer, so the scoreboard was mine.

It's a small app. 42 people, 6 teams of 7, six office days that count. It also has demanding users. The office includes IT people and automation testers. If the score lives in the browser, someone will change it in the browser. Not to cheat. Because it's funny.

So the one rule that shaped everything: the page is only a view. Every rule lives on the server.

One page, one function, one JSON file

The whole thing is a static HTML page with inline CSS and JavaScript. No framework, no build step. It has tabs for today's colour, the leaderboard, finding your team, the nine-colour calendar, the rules, bingo, and a scorekeeper desk that only appears after login.

Behind it sits one Netlify Function at /api/navratri. All state is one JSON document in Netlify Blobs. No database. For 42 people over nine days, a database is more to run than the problem is worth.

One file means one risk: two writes at the same moment, and the second silently overwrites the first. The fix is optimistic locking. Read the document with its ETag, change it, and write it back only if the ETag still matches. If someone else wrote in between, read again and retry.

// Read-modify-write with optimistic locking so two writes never clobber each other.
async function mutate(store, key, init, fn) {
  for (let attempt = 0; attempt < 5; attempt++) {
    const found = await store.getWithMetadata(key, { type: 'json' });
    const state = found ? found.data : init();
    const result = await fn(state);
    if (result && result.abort) return result;
    const res = found
      ? await store.setJSON(key, state, { onlyIfMatch: found.etag })
      : await store.setJSON(key, state, { onlyIfNew: true });
    if (res.modified) return result;
  }
  throw new Error('Busy — please try again');
}

Five attempts, then a clear error. Nothing is ever lost quietly.

Score the exceptions, not the rule

The first version asked the scorekeeper to tick everyone who came in colour. That's 42 ticks a day. Nobody does that properly by day three.

Most people do show up in colour. So now everyone counts as ✓ by default from 5 PM on each office day. The scorekeeper marks only the exceptions: ✗ for not in colour, or absent. Missing the colour scores zero, not a minus. Less to enter, fewer mistakes, and the mistakes left are the visible ones.

Assume someone will try

Everything below is enforced on the server. The page can be edited, replayed or scripted, and none of that changes a score.

  • No password in the repo. Only a slow scrypt hash. Comparison is constant-time.
  • Lockouts. Five wrong logins from one network locks that network out for 15 minutes. Thirty in total locks the login for everyone for 15 minutes. Failed logins show up in the public log.
  • Sessions are signed tokens that expire after four hours. The signing secret is generated on the server and stored with the data, never in the code. "Sign out all devices" kills every session at once.
  • Same-site JSON only. A script on another site can't post a score.
  • Every award is validated. The day must be an office day that has already happened. Points must be in range. Names must be on the roster. One dress-code point per person per day. Snack points only for that day's host team. Extra bonus is capped at 8 per team. Penalties need a reason.

Nothing gets deleted quietly

This mattered more than the login. In an office competition the real threat isn't someone hacking the scoreboard. It's someone saying the scorekeeper is biased.

So every change goes into a public transparency log. Mistakes are fixed with soft deletes, and every removal carries a reason anyone can read. If a point disappears, the log says when and why. That answers the question before anyone asks it.

What I cut

There was a forfeit wheel. If you weren't in colour, you spun it, and the server picked the forfeit at random so nobody could rig it. It worked. Then we decided forfeits are more fun done in person, in the office. The wheel is switched off behind a flag.

Some early categories didn't survive either. Their old entries still display, but the server rejects new ones.

Tests

The server is tested with Node's built-in test runner and an in-memory stand-in for Blobs. The tests cover cross-site and anonymous writes being refused, the lockout after five wrong logins, the scoring rules, attendance, the forfeit spin and its undo, absent marks, and refused forfeits. Two more check the page: that its inline script compiles, and that page and server agree on the app version.

Same rules as fintech

My day job is software that handles other people's money. This was a festival scoreboard. The rules were the same: never trust the client, log every change, and make the honest path the easy one.
