Reading financial PDFs without letting them leave the machine

An offline document sorter for invoices, POs and receipts. It used to have an LLM. I deleted it.

Dhruv Parekh·17 Oct 2026·4 min read

Document Sorter takes a pile of financial PDFs, such as invoices, purchase orders, receipts and transaction records. It works out what each one is and pulls out the company, address, date, amount and reference numbers. Then it groups the documents that belong together.

One rule decided the design: these are financial documents, so nothing leaves the machine. No API call, no cloud OCR, no model hosted somewhere else. It has to work with the network cable pulled out.

I deleted the AI

An earlier version used a hosted LLM to classify documents. After that came two locally fine-tuned models. At one point several interchangeable backends all read the same schema.

I removed all of them. There were two reasons, and both are written down in the repo's decision log. First, it has to be able to run air-gapped. Second, I wanted a pipeline I can read and reason about, not one whose behaviour is a training artefact. When a classification is wrong, I want to point at the line that made it wrong.

Now the pipeline makes zero API calls and uses no trained model of its own. The one thing that could be called a model is the OCR engine. It's fixed, pre-trained and runs locally.

The pipeline

  1. Text extraction. pdf-parse pulls the embedded text.
  2. OCR fallback. If a document has fewer than 25 letters and digits, it's treated as scanned. Pages are rendered at 2× and cleaned up: upscaled if narrow, grayscale, a 3×3 median filter, then Otsu thresholding. Then they go to Tesseract.
  3. Classification by weighted keyword scoring.
  4. Field extraction with regex and layout heuristics.
  5. Grouping with union-find.

A war story from step one. I first used a second PDF library to render pages for OCR. Both libraries carry their own copy of pdf.js, and two copies in one process corrupt each other's global state. The fix was to use one library for both text and page images.

OCR with no network

Tesseract runs as WebAssembly through tesseract.js. By default it fetches its engine and language data from a CDN the first time it runs, which is exactly what can't happen here. So every path points at files installed with the package and resolved from disk:

workerPromise = createWorker('eng', 1, {
  langPath: resolveLangPath(),
  corePath: resolveCorePath(),
  workerPath: resolveWorkerPath(),
  gzip: true,
  cacheMethod: 'none', // don't try to write/read a cache dir; the local file is authoritative
  // No `logger` — keep OCR quiet; progress isn't useful in a batch run.
});

cacheMethod: 'none' stops it from writing a cache anywhere. One worker is shared, and all recognition calls run through a single queue.

Classification is arithmetic

Every document type has a list of keywords and a weight. A document gets the weight for every keyword it contains, and the highest score wins:

for (const rule of buildClassificationRules()) {
  const score = rule.keywords.reduce((sum, re) => (re.test(collapsedText) ? sum + rule.weight : sum), 0);
  if (score > bestScore) {
    bestScore = score;
    best = rule.type;
  }
}

A score of zero means "Unknown". Because the comparison is strictly greater-than, a tie goes to whichever type comes first in the config. Not clever, but predictable.

The config is the product

Document types, fields, extraction rules and branding all live in one JSON file. A new client with a different mix of documents needs a config change, not a code change. One document type:

{
  "name": "Invoice",
  "description": "Commercial invoices, tax invoices, bills — a request for payment from seller to buyer.",
  "keywords": ["Tax Invoice", "Commercial Invoice", "Invoice To", "Bill To", "Total Due", "Amount Due", "Invoice No", "GSTIN"],
  "keywordWeight": 5
},

And one field. The isBatchKey flag matters later:

{
  "name": "documentNumber",
  "description": "The primary identifying number for this document — invoice number, receipt number, transaction ID, etc.",
  "extractor": "labeledId",
  "labels": ["Invoice No", "Invoice Number", "Inv No", "Inv #", "Receipt No", "Receipt Number", "Transaction ID", "Transaction No", "Bill No", "Reference No", "Ref No"],
  "appliesTo": ["Invoice", "Transaction Record", "Receipt"],
  "isBatchKey": true
},

Extractors are named in the config and dispatched by name. The amount extractor takes the last number on a line labelled as a total. Failing that, it takes the largest number formatted like money, and bare integers don't count. The company extractor looks for a corporate suffix in the first 15 lines.

Grouping: union-find

An invoice, its purchase order and its payment receipt often share a reference number. Any two documents that share a value in a batch-key field are joined. Union-find makes that cheap, and it handles chains. If A shares a number with B, and B with C, all three end up together.

class UnionFind {
  constructor(size) {
    this.parent = Array.from({ length: size }, (_, i) => i);
  }

  find(i) {
    if (this.parent[i] !== i) this.parent[i] = this.find(this.parent[i]);
    return this.parent[i];
  }

  union(a, b) {
    const rootA = this.find(a);
    const rootB = this.find(b);
    if (rootA !== rootB) this.parent[rootA] = rootB;
  }
}

Groups of one go into "unbatched", so nothing silently disappears.

The web UI

An Express server takes up to 200 PDFs per upload, 25 MB each, PDFs only. Files are held in memory and never written to disk. Four documents are processed at once, and OCR stays on its single queue.

Where it breaks

The README has a whole section on this, and I'd rather lead with it than have someone find out:

  • "These are heuristics over messy real-world documents, not a solved problem."
  • Company name and address are the weakest fields.
  • Dates are returned as printed, never normalised.
  • "Classification is keyword scoring, not understanding."
  • OCR is only as good as the scan, and rotated pages aren't handled.
  • English only. No table awareness. No confidence scores.
  • The scanned-or-not decision is made per document, not per page.

That list is where the work is. It's also why the heuristics are plain code. Each fix is a change I can read, test and explain to whoever owns the documents.
